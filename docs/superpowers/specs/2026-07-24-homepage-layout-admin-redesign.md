# Homepage Layout Admin Redesign

วันที่: 2026-07-24  
สถานะ: อนุมัติแนวทาง UI แล้ว รอตรวจเอกสารก่อนวางแผนพัฒนา

## เป้าหมาย

ปรับหน้า `/admin/sections` ให้ผู้ดูแลแยกได้ทันทีว่าแต่ละรายการเป็นชุดบ้านพัก (Rail) หรือ Section ของระบบ พร้อมลดความรกจากการแสดงการจัดลำดับ สถานะ และแบบฟอร์มจำนวนมากในระดับความสำคัญเดียวกัน

ผู้ดูแลต้องสามารถ:

- เห็นโครงหน้าแรกและลำดับ Section ได้จากรายการเดียว
- ลากจัดลำดับและเปิดหรือปิด Section ได้จากภาพรวม
- เลือก Section แล้วแก้รายละเอียดในพื้นที่ Editor ที่แยกชัดเจน
- แยก Rail บ้านพักออกจาก Section ระบบได้โดยไม่ต้องอ่านรายละเอียดทั้งหมด
- บันทึกและเปิดหน้าเว็บจริงได้จากแถบคำสั่งหลัก

## แนวทางที่เลือก

ใช้ Master–Detail แบบสองคอลัมน์บน Desktop:

- คอลัมน์ซ้ายเป็นโครงหน้าแรก แสดงลำดับและสถานะของทุก Section
- คอลัมน์ขวาเป็น Editor ของรายการที่เลือก
- Hero อยู่บนสุดและล็อกตำแหน่งเหมือนพฤติกรรมปัจจุบัน
- ลดคำอธิบายซ้ำและการ์ดซ้อน โดยใช้เส้นแบ่งและหัวข้อสั้นแทน

บนหน้าจอแคบ รายการโครงหน้าและ Editor เรียงเป็นคอลัมน์เดียว โดยแสดงรายการก่อน Editor และต้องไม่เกิด horizontal overflow

## ภาษาภาพและกติกา Icon

Icon ใช้เพื่อบอก “ประเภท” ก่อนบอกรายละเอียด และต้องมีข้อความกำกับเพื่อไม่พึ่งสีหรือ Icon เพียงอย่างเดียว

### Rail บ้านพัก

- Rail ทุกชนิดใช้ไอคอน `House` เหมือนกัน
- ไม่เปลี่ยน Icon ตามเงื่อนไขของ Rail เช่น บ้านใกล้ทะเล บ้านแนะนำ หรือบ้านที่เลือกเอง
- แสดงป้ายข้อความ `ชุดบ้านพัก`
- เงื่อนไขการเลือกบ้าน เช่น Manual, Near Sea หรือ Slice แสดงเป็นข้อความสถานะ ไม่ใช้ Icon ประเภทใหม่

### Section ของระบบ

ใช้ Icon ตามหน้าที่ของเนื้อหา:

| Section | Icon |
| --- | --- |
| Hero | `PanelsTopLeft` |
| ทำไมต้องเลือกเรา | `BadgeCheck` |
| TikTok | `Video` |
| รีวิวจากลูกค้า | `MessageSquareHeart` |
| บทความ | `Newspaper` |
| FAQ | `CircleHelp` |
| ติดต่อ | `Phone` |

ทุก Section ระบบแสดงป้ายข้อความ `ส่วนของระบบ`

### สถานะ

- สถานะเปิดหรือปิดต้องมีข้อความเสมอ
- สีใช้เสริมการรับรู้เท่านั้น ไม่ใช้แทนข้อความ
- รายการที่เลือกต้องมีทั้งพื้นหลังหรือเส้นขอบที่ต่างออกไปและ `aria-pressed`
- Hero แสดง Icon ล็อกและข้อความ `บนสุดเสมอ`

## โครงหน้าจอ

### แถบคำสั่ง

แสดงเฉพาะข้อมูลและคำสั่งที่จำเป็น:

- ชื่อหน้า `จัดหน้าแรก`
- สถานะ `บันทึกล่าสุดแล้ว` หรือ `มีการแก้ไขที่ยังไม่บันทึก`
- ปุ่ม `ดูหน้าเว็บ`
- ปุ่มหลัก `บันทึก`

ปุ่ม `เพิ่มชุดบ้านพัก` อยู่ท้ายรายการโครงหน้า เพราะเป็นการเพิ่มรายการใน Master ไม่ใช่คำสั่งระดับทั้งหน้า

### รายการโครงหน้า

แต่ละแถวประกอบด้วย:

1. Drag handle หรือ Lock สำหรับ Hero
2. Icon ประเภท
3. ชื่อ Section
4. ป้ายประเภท
5. สถานะหรือสรุปสั้น เช่น `8 หลัง`, `อัตโนมัติ`, `6 คลิป`, `เปิด` หรือ `ปิด`

การคลิกแถวเลือก Editor แต่ไม่เปลี่ยนสถานะเปิดหรือปิดโดยไม่ตั้งใจ การลาก การเลือก และการเปิดหรือปิดต้องเป็น interaction คนละจุด

### Editor

ส่วนหัว Editor แสดง Icon, ป้ายประเภท, ชื่อ Section และสวิตช์แสดงบนหน้าแรก

สำหรับ Rail บ้านพัก แบ่งข้อมูลเป็นสามกลุ่ม:

1. ข้อความที่ลูกค้าเห็น
2. วิธีเลือกและจำนวนบ้าน
3. บ้านที่เลือกหรือสรุปกติกาอัตโนมัติ

สำหรับ Section ระบบ แสดงคำอธิบายสั้นและลิงก์ไปยังหน้าที่เป็นเจ้าของข้อมูลเดิม เช่น TikTok, รีวิว, บทความ และข้อมูลติดต่อ โดยหน้า Layout จัดการเฉพาะลำดับและสถานะการแสดงผล

## Data Flow และขอบเขต

การปรับครั้งนี้เป็นการจัดระเบียบ Presentation และ Interaction ของหน้า Admin:

- ใช้ `HomePageLayoutItem` และ `AdminSectionDraft` เดิม
- ใช้ GET/PUT `/api/admin/home-sections` เดิม
- ใช้ snapshot, validation, warning และ save flow เดิม
- ไม่เพิ่มหรือลบตาราง Supabase
- ไม่เปลี่ยน public homepage rendering
- ไม่เปลี่ยน cache หรือ revalidation policy
- ไม่ย้าย ownership ของเนื้อหา Section ระบบ

ควรแยก component ตามหน้าที่โดยใช้เจ้าของเดิมใน `components/admin/sections` เช่น:

- รายการโครงหน้าและแถว Section
- ส่วนหัว Editor
- Editor ของ Rail
- Panel แนะนำทางไปยังหน้าจัดการ Section ระบบ

ไม่สร้าง abstraction ใหม่สำหรับ API หรือ state management ที่มีผู้ใช้เพียงจุดเดียว

## Validation และ Error Handling

- รักษาการ map validation error ไปยัง Section และ field เดิม
- เมื่อบันทึกแล้วพบ error ให้เลือก Section แรกที่ผิดและเลื่อนไปยัง field ที่เกี่ยวข้อง
- Error, warning และ success feedback ต้องอยู่ใกล้แถบคำสั่งและอ่านได้หลัง scroll
- การลบ Rail ต้องมีขั้นยืนยันเหมือนเดิม
- ปุ่มบันทึก disabled ระหว่างโหลด ระหว่างบันทึก หรือเมื่อไม่มีการเปลี่ยนแปลง
- การนำทางออกจากหน้าขณะมี draft ที่ยังไม่บันทึกต้องรักษาพฤติกรรมป้องกันข้อมูลสูญหายเดิม

## Accessibility

- ทุกปุ่ม Icon-only ต้องมี accessible name
- Icon ที่เป็นเพียงภาพประกอบใช้ `aria-hidden="true"`
- รายการที่เลือกใช้ semantic button และ `aria-pressed`
- สวิตช์เปิดหรือปิดมี label ที่มองเห็นได้
- Drag-and-drop ต้องคงปุ่มเลื่อนขึ้นและลงสำหรับผู้ใช้คีย์บอร์ด
- Focus state ต้องมองเห็นชัด
- ป้ายประเภทและข้อความสถานะต้องยังแยกความหมายได้ในโหมดสีต่าง ๆ

## Responsive Behavior

- Desktop: Master 280–340px และ Editor ใช้พื้นที่ที่เหลือ
- Tablet และ Mobile: เรียง Master ก่อน Editor
- ปุ่มคำสั่ง wrap ได้โดยไม่ทับชื่อหน้า
- ชื่อยาว สถานะ และป้ายประเภทต้อง wrap หรือ truncate อย่างปลอดภัย
- Editor form เปลี่ยนจากหลายคอลัมน์เป็นคอลัมน์เดียวเมื่อพื้นที่ไม่พอ

## การทดสอบและตรวจสอบ

เพิ่มหรือปรับ focused tests สำหรับ:

- Rail ทุกชนิดแสดง Icon บ้านและป้าย `ชุดบ้านพัก`
- Fixed Section แต่ละชนิดแสดง Icon และป้ายที่ถูกต้อง
- การเลือกแถวเปลี่ยน Editor โดยไม่เปลี่ยน enabled state
- Hero ถูกล็อกและไม่สามารถเปิด Editor สำหรับแก้ข้อมูลที่ไม่ได้เป็นเจ้าของได้
- การเลื่อนลำดับ เปิดหรือปิด เพิ่ม ลบ และบันทึกยังสร้าง snapshot เดิม
- Validation error เลือก Section และ focus field ที่ถูกต้อง
- Layout ใช้งานได้ทั้ง Mobile และ Desktop

ก่อนถือว่างานเสร็จ ต้องรัน:

- Targeted Vitest สำหรับ `components/admin/sections`
- `npm.cmd run lint`
- `npm.cmd run build`
- เปิด `/admin/sections` ใน browser และตรวจ Desktop/Mobile รวมถึง loading, error, long text และ unsaved state

## เกณฑ์ยอมรับ

ถือว่างานสำเร็จเมื่อ:

- ผู้ใช้บอกประเภทของรายการได้จาก Icon และป้ายโดยไม่ต้องเปิด Editor
- Rail ทุกประเภทใช้ Icon บ้านอย่างสม่ำเสมอ
- Section ระบบมี Icon ที่สัมพันธ์กับเนื้อหา
- งานจัดลำดับและงานแก้รายละเอียดมีลำดับสายตาแยกจากกัน
- ความสามารถเดิมของหน้า Admin และ public homepage ไม่ถดถอย
- ไม่มีการเปลี่ยน API, schema หรือ cache โดยไม่จำเป็น
